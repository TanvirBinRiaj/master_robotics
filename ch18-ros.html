ROS 2: The Robot Operating System

As robots grow, one big program stops working. ROS lets you split the job into small programs that talk to each other. By the end, you will understand nodes, topics and messages, and you will design a ROS graph for your own robot.

~27 min read Intermediate Chapter 18 of 30

What you will learn

  • Explain what ROS is and why it exists.
  • Describe nodes, topics and messages.
  • Run a first ROS-style program idea.

Imagine you are building a delivery robot. One small program reads the camera. Another reads the wheels. Another decides where to go. Another drives the motors. Now imagine keeping all of that inside one giant file. Every small change risks breaking everything else. This is the exact problem ROS was built to solve.

The problem ROS solves

A robot has many jobs to do at the same time. It must read sensors. It must decide what to do. It must drive motors. It must watch its battery. It must talk to a screen or a phone. If you write all of this as one program, the program quickly becomes huge.

A huge program is hard to change. Fix the wheel code and you might break the camera code. Two people cannot work on the same file easily. You cannot test one small part on its own. And you cannot copy a good piece of code from an old robot into a new one.

Engineers solve this the same way a busy restaurant does. They do not hire one cook who does everything. They hire many workers, each with one clear job. The vegetable cook chops vegetables. The sauce cook makes sauce. They pass plates to each other. The kitchen runs smoothly because each person has one task and a clear way to hand work to the next person.

ROS does this for robot software. It lets you split a robot into many small programs, each with one job. It also gives those programs a shared language so they can pass data to each other. And it gives you a shared toolbox, so you can reuse work that other people already did.

The key idea

ROS is a shared set of software tools and a shared language for building robot programs. It lets many small programs work together, and it lets people reuse each other's work.

What ROS actually is

First, let us clear up the name. The full name of ROS is Robot Operating System. This name confuses almost everyone at first, so read this part carefully.

ROS is not an operating system

An operating system is the main software that runs a computer. Windows, macOS and Linux are operating systems. They manage memory, files, screens and hardware. ROS does none of that. You cannot install ROS on a bare computer and use it instead of Linux.

ROS runs on top of a normal operating system, usually Linux. It also works on Windows and macOS. So the name is misleading. ROS is not an operating system at all.

What ROS really is

ROS is three things bundled into one project:

  • Middleware. This is the hidden plumbing that moves data between programs. Middleware sits in the middle and carries messages from one program to another without you writing the network code yourself.
  • A set of libraries. A library is ready-made code you can call. ROS libraries handle common tasks like reading a sensor, moving a robot, or talking to a camera.
  • A set of tools. These are small programs that help you watch, test and control your robot while it runs.

Put together, ROS is the shared toolbox and the shared language for robot software. It is not the robot's brain by itself. It is the workshop where you build the brain.

In simple words

ROS is not Windows or Linux. It runs on top of those. ROS is a box of ready-made tools plus a way for your robot's programs to talk to each other.

Nodes: one program, one job

The smallest building block in ROS is a node. A node is one program that does one job. That is the whole rule. If a program has one clear job, it is a good node. If a program tries to do five jobs at once, it should be split into five nodes.

Examples of nodes in a real robot:

  • A node that reads the distance sensor and reports the numbers.
  • A node that reads the camera and finds lines on the floor.
  • A node that plans a path from one place to another.
  • A node that sends speed commands to the motors.
  • A node that watches the battery and warns when it is low.

Each of those is a separate, small program. Each one is easy to test alone. Each one can be replaced or improved without touching the others.

Why one job per node matters

Think of a team of workers again. If one worker has a single clear task, you can tell exactly who is responsible when something goes wrong. You can swap that worker for a better one. You can give the same task to two workers and compare them. Nodes work the same way.

The usual exception is a tiny robot with only one useful job. Then one node is fine. But as soon as your robot grows, splitting the work pays off.

Note

A node usually does not care where its data comes from or who uses its output. It just asks ROS for data and sends its own data out. This is what makes nodes so easy to connect and reuse.

Topics: named channels for data

Nodes need to share data. ROS does this with topics. A topic is a named channel that carries a stream of data. Think of a name like /camera/image or /motor/speed.

Topics use a simple pattern called publish and subscribe. A node that has data publishes it by putting it on a topic. A node that wants that data subscribes to the topic and receives it. Publishers send. Subscribers listen.

The notice board picture

Imagine an office with many notice boards on the wall. Each board has a name, like "Weather" or "Lunch menu". Anyone who has news pins a note to the right board. Anyone who wants to know reads the board. The people pinning notes never meet the people reading them. They only share the board.

A ROS topic is exactly that board. The publisher pins a message to a topic. Every subscriber reads it. The publisher does not know or care who is reading.

Many-to-many and asynchronous

Two words describe how topics work. They sound technical but they are simple.

Many-to-many means any number of publishers and any number of subscribers can share one topic. One camera node might publish an image, and five different nodes might read it.

Asynchronous means the publisher does not wait for a reply. It pins its note and moves on. If no one is listening, nothing breaks. This keeps nodes fast and independent. That is the opposite of a phone call, where you must wait for the other person to answer.

Message rate on a topic rate = number of messages ÷ time in seconds

Here is a small, useful calculation. Suppose a camera node publishes 30 images every second. If you record it for 10 minutes, how many messages do you have?

30 messages per second × 600 seconds = 18,000 messages. If you recorded for one hour, it would be 30 × 3,600 = 108,000 messages. This is why professionals record data carefully. A fast topic fills up storage very quickly.

Messages: the typed data on a topic

A topic carries data in small packages called messages. A message has a fixed shape and fixed types. Think of it like a form with labelled boxes, so every reader knows exactly what to expect.

For example, a distance message might hold one number: a distance in metres. The type of that number is a float, which means a number with a decimal point, like 1.25. An image message is bigger. It holds the image width, the image height, how the colours are stored, and the picture data itself.

Why types matter

Computers take types very seriously. A float is a number with decimals. An integer is a whole number. A string is text. A boolean is true or false. If you try to put text where a number belongs, the program fails.

Types protect you. Because the message shape is agreed in advance, a subscriber knows exactly what it will receive. It knows the distance is a float in metres, not a string of text or a picture. The publisher and subscriber do not need to guess. This rule catches many mistakes before the robot ever moves.

Services: a request and a reply

Topics are great for steady streams, but sometimes you want an answer. You want to ask one node a question and get one reply. That is a service.

A service works like a phone call. One node asks a question and waits for the answer. This is called request and reply, and it is one-to-one. Only one node answers your request.

Good uses for a service:

  • "Take a picture right now and send it to me."
  • "Switch the lights on."
  • "What is your battery level?"
  • "Save a map of this room."

Notice the pattern. Each of these is a one-time job with a clear answer, not a continuous stream. If you asked a camera to publish pictures on a topic, that is a stream. If you asked it to snap one photo and hand it back, that is a service.

Watch out

A service blocks the caller until the reply arrives. If the service is slow, the asking node freezes while it waits. That is why long jobs are not done with services. For long jobs, ROS gives us actions.

Actions: long jobs with progress

Some jobs take a while and should report progress along the way. Think of "drive to the kitchen". That is not instant. The robot must move for many seconds and you may want to know how far along it is. It should also be possible to cancel it halfway.

An action is built for exactly this. You send a goal, such as "drive to the kitchen". The robot accepts it. While it works, it keeps sending feedback, such as "60 percent of the way there". When it finishes, it sends a final result. At any moment you can cancel the goal, and the robot will stop safely.

So the three ways to communicate in ROS fit three different needs. A topic is a fire hose of data. A service is a phone call with one answer. An action is a long errand with progress updates and a cancel button. Choose the one that matches your job.

Parameters: settings a node reads at start

A parameter is a named setting that a node reads when it starts or while it runs. Wheel diameter, robot width, maximum speed and camera resolution are all parameters.

Why not just write those numbers inside the code? Because you will change them. If the wheel diameter is buried deep in the code, you must edit the program and rebuild it every time you swap a wheel. With a parameter, you set the number in one place and the node reads it.

Parameters make one node reusable. The same motor-driver node can drive a tiny robot or a large one. Only the wheel diameter parameter changes. The code stays the same.

Tip

A good habit: if a number describes the robot or the world, make it a parameter. If a number is a fixed rule of maths, keep it in the code.

Seeing the graph: the whole robot at a glance

When you connect many nodes with topics, a picture appears. ROS calls it the graph. Nodes are circles. Topics are the arcs or arrows between them. Services and actions also appear.

The graph is one of the best ideas in ROS. It lets you look at your whole robot as one clear picture. You can see which node sends data and which node receives it. If a topic has no publisher, you can spot the missing piece at once.

Read Figure 18.2 like a story. The sensor node measures the distance and publishes a float on the /scan topic. The controller node subscribes to /scan, decides what to do, and publishes two floats on /motor/cmd. The motor node subscribes to /motor/cmd and turns the wheels. Each node has one job, and each topic carries one type of message.

The toolbox: commands, viewers and simulators

ROS comes with tools that help you see and control your robot. You use them from a terminal, which is a text window where you type commands. You do not need to memorise all of them. You need to know what each one is for.

The command line

Every ROS command starts with the word ros2. That is the name of the current ROS line. Here are the commands you will use most, in plain words:

  • ros2 node list — show every running node. "Who is working right now?"
  • ros2 topic list — show every topic. "What channels exist?"
  • ros2 topic echo <name> — print the messages flowing on a topic. "What data is on this channel?"
  • ros2 run <package> <node> — start one node from a package.
  • ros2 launch <package> <file> — start many nodes at once from a launch file.
Terminal 
# see what is running
ros2 node list
ros2 topic list

# watch the data on a topic, one message at a time
ros2 topic echo /scan

# start a single node, then start a whole robot
ros2 run my_robot distance_node
ros2 launch my_robot bringup.launch.py

Seeing the data and testing without hardware

RViz is a viewer. It shows your robot's data as pictures: point clouds, maps, camera images and the robot's guessed position. Instead of reading numbers, you watch the robot's world on screen. It is built into ROS and needs no external images.

Gazebo is a simulator. It is a pretend world with gravity, physics and virtual sensors. You can test your robot software in Gazebo before you own the real robot. If the robot crashes in simulation, only the pixels get hurt. This is one of the biggest reasons professionals love ROS.

In simple words

The command line lets you peek at your robot. RViz draws what the robot senses. Gazebo is a practice world where you can crash safely.

Packages, workspaces and launch files

Before you write real code, three words explain how a ROS project is organised.

Package

A package is one folder that holds related nodes, messages and settings. A package is the unit you share. For example, a "motor" package might hold the motor node, its message types and its parameter file. When someone says "use the navigation package", they mean one ready-made folder of code you can drop into your robot.

Workspace

A workspace is a folder that holds many packages for one project. Think of it as a workbench. You keep all your own packages in one workspace, build them once, and ROS knows where to find them. You build a workspace with a single command, and ROS creates the setup files that your terminal must load before it can find your code.

Launch file

A launch file is a recipe that starts many nodes at once. A real robot may need ten nodes running together. Instead of typing ten ros2 run commands every time, you write one launch file. You run it with ros2 launch, and every node starts in the right order with the right parameters. This one file turns "start the robot" into a single command.

Note

Launch files matter for beginners too. Many first-run failures happen only because one node was forgotten. A launch file makes sure every node of the robot is started together, every time.

Your first idea: moving a virtual turtle

The classic first ROS program uses a small simulator called turtlesim. It shows a flat window with a turtle. If you send it a speed command, the turtle draws a line as it moves. Nothing can crash, so it is a safe place to learn.

Here is how the pieces fit. One node is the turtle itself. It subscribes to a command topic. When it receives a message holding a forward speed and a turn speed, it moves the turtle. So the way to move the turtle is to publish a message to that command topic. You become a publisher node.

  1. Start the turtle node. Run the turtlesim node. A window opens with the turtle in the middle.
  2. Look at the topics. Run ros2 topic list and find the command topic. It is usually called /turtle1/cmd_vel.
  3. Read the message shape. Ask ROS for the message type on that topic. You will see it holds two parts: a linear speed and an angular speed.
  4. Publish a command. Send a message with forward speed 2 and turn speed 0. The turtle drives straight.
  5. Watch it echo. In another terminal, run ros2 topic echo on the same topic and watch your own messages appear.

This is the heart of ROS in one exercise. A node waits on a topic. You publish to that topic. The node reacts. That is a complete publish and subscribe loop, and it repeats everywhere in real robots.

Now look at it as code. This is a simple publisher in Python style. Read the comments to follow the steps.

Python (ROS 2 style) 
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Twist

class TurtleDriver(Node):
    def __init__(self):
        super().__init__('turtle_driver')
        # publish speed messages on the turtle's command topic
        self.pub = self.create_publisher(Twist, '/turtle1/cmd_vel', 10)
        # send a command twice per second
        self.timer = self.create_timer(0.5, self.send_command)

    def send_command(self):
        msg = Twist()
        msg.linear.x = 2.0     # forward speed
        msg.angular.z = 0.5    # gentle left turn
        self.pub.publish(msg)  # pin the note to the topic

rclpy.init()
node = TurtleDriver()
rclpy.spin(node)           # keep the node alive and working

Do not worry about every symbol yet. Notice the shape of the program. It makes a node. It creates one publisher on one topic. On a timer, it builds a message, fills the numbers, and publishes. The turtle reads the topic and moves. That is the whole idea of a ROS program.

A worked example: the line-following robot

Let us design a complete ROS graph from scratch. This is the kind of thinking professionals do before writing a single line of code. We will design a mobile robot that follows a line on the floor.

Step 1: write the job in plain words

The robot must drive along a dark line on a light floor. A camera looks down at the floor. The robot should keep the line in the middle of its view. If the line drifts left, the robot turns left. If the line drifts right, the robot turns right. It should move forward at a steady speed while doing this.

Step 2: list the jobs, one per node

Now split the work into single jobs. Four nodes are enough to start.

  1. Camera node. Reads the camera and publishes images. One job: capture pictures.
  2. Line finder node. Reads images and finds the line's position. One job: turn a picture into a number that says how far the line is left or right of centre.
  3. Controller node. Reads the line position and decides the wheel speeds. One job: choose the commands.
  4. Motor node. Reads the speed commands and drives the wheels. One job: make the robot move.

Step 3: name every topic and choose a message type

Now connect the nodes with topics and give every topic a message type. Table 18.3 is the full design.

Step 4: follow the data flow

The camera node publishes an image on /camera/image thirty times a second. The line finder subscribes to that topic. It looks at each picture and works out where the line sits. It publishes one float on /line/offset. A negative number means the line is to the left. A positive number means it is to the right. Zero means the line is centred.

The controller subscribes to /line/offset. If the number is zero, it sends equal speeds to both wheels, so the robot goes straight. If the number is slightly negative, it slows the left wheel and speeds the right wheel, so the robot curves left. It publishes those two speeds on /motor/cmd. The motor node reads them and drives the wheels. Then the camera takes the next picture, and the loop repeats.

Step 5: add the settings as parameters

We keep the robot's numbers out of the code. The motor node reads the wheel diameter and the wheel spacing as parameters. The controller reads the forward speed and the turn gain as parameters. If the robot's wheels change size, we update one parameter. The nodes never change.

Step 6: check the graph

Run ros2 node list and you should see four nodes. Run ros2 topic list and you should see /camera/image, /line/offset and /motor/cmd. Run ros2 topic echo /line/offset and wiggle a piece of tape under the camera. The number should change. If it does, your design is alive.

Tip

Design the graph on paper first. List the nodes, then the topics, then the message type for each topic. Most ROS bugs are found at this stage, before any code exists.

Why professionals use ROS, and its trade-offs

ROS is not the only way to build robot software. So why do so many professionals choose it? Because it gives them several big wins at once.

  • Reuse. Thousands of ready-made packages exist. Need navigation? Someone already wrote it. You build on their work instead of starting from zero.
  • Modularity. Each node is small and replaceable. You can improve one node without touching the rest.
  • Community. A large community shares code, answers questions and fixes bugs. You are never alone with a hard problem.
  • Simulation. You can test in Gazebo before owning hardware, which saves money and prevents real damage.
  • Standard tools. Commands, viewers and recording tools work the same on every ROS robot, so skills transfer between jobs.

But ROS is not free of cost. It has real trade-offs you should know before you commit.

  • Learning curve. Nodes, topics, packages and launch files take time to learn. The first week feels slow.
  • Overhead. Splitting work into nodes adds message-passing cost. For a tiny task, a single simple program can be faster and simpler.
  • Not for tiny microcontrollers. A small microcontroller with little memory cannot run full ROS. The usual answer is to run a tiny ROS client on the board, or pair the board with a larger computer that runs ROS and talks to the board over a serial link.
Watch out

Do not put ROS on everything just because you can. A motor driver on a small chip does not need ROS. Let the big computer run ROS, and let the small chip do its one simple job well.

Common mistakes beginners make

These are the usual traps. Knowing them in advance will save you many hours.

  • One giant node. Beginners put every job in one node. Then it is hard to test and impossible to reuse. Split it. One job per node is the rule.
  • Hard-coded parameters. Wheel size, speed and robot width written inside the code. Change the robot and you must rewrite the program. Put these in parameters instead.
  • Blocking callbacks. A callback is the small function that runs when a message arrives. If it does slow work, such as waiting three seconds, it stops every other message. Keep callbacks short and move slow work elsewhere.
  • Ignoring timestamps. Every message carries the time it was made. If you mix old and new data, your robot reacts to the past. Always check the timestamp before you trust a reading.
  • Wrong message types. A subscriber expects one exact type. If the publisher sends a different one, nothing connects and no data flows. Always confirm the type on the topic.
  • Running before sourcing the setup. Before your terminal can find your packages, it must load the workspace setup file. If you forget, ROS says the package does not exist. Load the setup first, every new terminal.
Dangerous habit

Do not test a new ROS graph on a real moving robot at full speed. Test node by node, then in a simulator, then on blocks with the wheels off the floor. Only then let it drive. A wrong topic can send a robot across a room.

How professionals do it

Once you understand the basics, this is how working engineers use ROS every day.

ROS 2 is the current line

There are two generations. The older one is called ROS 1. The current one is ROS 2, and it is what new projects use. ROS 2 has named releases, called distributions, such as Foxy, Humble and Jazzy. Each release is supported for a set number of years. Professionals pick a long-support release for a product, so they do not have to upgrade constantly.

DDS under the hood

ROS 2 sends messages using a proven system called DDS, the Data Distribution Service. In one line: DDS is the reliable plumbing that finds nodes and moves their data across the network, even between different computers on the robot. You almost never touch it, but it is why ROS 2 works smoothly across many machines.

Real-time concerns

Some robots must react within a guaranteed time, every time. This is called real-time behaviour. A normal computer and normal ROS do not promise this. Professionals use special real-time settings and often keep the most time-critical loop on a dedicated controller, not in the main ROS graph.

Bag files for recording

A bag file records the messages flowing on your topics while the robot runs. Later you can replay that recording, exactly as if the robot were live. This is how professionals debug a rare failure. They record the bag, replay it on their desk, and watch the same event again and again.

Continuous testing

Professional teams run automatic tests every time they change the code. This is called continuous integration, or CI. The tests check that nodes start, topics publish the right message types, and the robot behaves in the simulator. This catches mistakes before they reach a real robot.

Try it yourself

These exercises need no ROS installation to start. They build the thinking you need before you touch real code.

  1. Draw your own robot's graph. Pick any robot you can imagine, such as a robot that waters a plant. Draw each node as a circle. Draw each topic as an arrow. Write the message type on every topic. Hint: if two nodes share a topic, they must agree on the same message type.
  2. Split a big program. Take a single program that does five jobs, such as a robot vacuum. List five nodes and the topic between each pair. Hint: one node should only ever do one job.
  3. Choose the right pattern. For each task, decide if it is a topic, a service or an action: (a) stream of wheel speeds, (b) "what is the time?", (c) "drive to the charging station". Hint: stream, one answer, or long job with progress.
  4. Make it a parameter. Look at any robot code you have written. Find every number that describes the robot or the world. Move those into a settings list. Explain why each one is now easier to change.
  5. Run the turtle. If you have ROS installed, start the turtlesim node and move the turtle with a command on its command topic. Then echo the topic in a second terminal and watch your own messages appear. Hint: the topic is usually /turtle1/cmd_vel.

Going deeper (optional)

One advanced idea for curious readers. On a real robot, many nodes are not on one computer. The camera may be a small board at the front, the main computer may sit in the middle, and a motor controller may be near the wheels. ROS 2 can spread the same graph across all of them. DDS finds the nodes over the network and moves messages between machines as easily as between programs on one machine.

This is called distributed computing, and it is why ROS scales from a toy turtle to a warehouse fleet. When you are ready, read about quality of service, or QoS. It lets you choose between "lose old data and stay current" and "never lose a message" for each topic.

Key takeaways

  • One huge program does not scale. ROS splits a robot into many small programs.
  • ROS is not an operating system. It runs on top of Linux, Windows or macOS.
  • A node is one program with one clear job.
  • Topics carry streaming data with publish and subscribe.
  • Messages are typed data, so every reader knows the exact shape.
  • Services are one-to-one request and reply. Actions are long jobs with feedback and a cancel button.
  • Parameters are settings a node reads, so you never hard-code the robot's size or speed.

Q1.Is ROS an operating system? Explain your answer.
Answer. No. Despite the name, ROS is not an operating system. It runs on top of a real operating system such as Linux, and it gives you middleware, libraries and tools for building robot software.
Q2.What is a node, and what is the rule for a good node?
Answer. A node is one program that does one job. A good node has one clear task, so it is easy to test, replace and reuse.
Q3.What does publish and subscribe mean?
Answer. A publisher sends data onto a named topic. Subscribers read that topic. The publisher does not wait for a reply and does not need to know who is listening.
Q4.Why do messages have types?
Answer. Types fix the shape of the data. A subscriber knows exactly what it will receive, such as a float distance in metres, so it does not have to guess and common mistakes are caught early.
Q5.When should you use a service instead of a topic?
Answer. Use a service for a one-time request that needs a single reply, such as "take a picture now" or "what is your battery level". Use a topic for continuous streams.
Q6.What does a parameter do, and why is it better than hard-coding a number?
Answer. A parameter is a named setting a node reads at start or while running. It lets you change values like wheel diameter in one place, so the same node works on different robots without editing and rebuilding the code.
Q7.In the line-following robot, what does the /line/offset topic carry, and who reads it?
Answer. It carries a single float: how far the line is from the centre, in metres, with negative meaning left. The line finder publishes it and the controller subscribes to it.
Q8.Name two reasons a professional might choose not to put full ROS on a small microcontroller.
Answer. A small microcontroller has limited memory and cannot run full ROS, and a simple single job does not need the extra message-passing overhead. The usual solution is a tiny ROS client on the board, or pairing the board with a larger computer that runs ROS.
