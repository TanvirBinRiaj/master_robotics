Production Software for Robotics

Demo code makes one robot move once. Production code makes many robots move every day. By the end, you will explain modern C++ and math libraries in plain words, set up a ROS 2 node with ros2_control, and describe real-time Linux, Docker, CI and testing.

  • Explain modern C++, Eigen and build tools in plain words.
  • Set up a ROS 2 node with the ros2_control idea.
  • Describe real-time Linux, Docker and CI, and testing.

Imagine two robots. The first one moves on your desk. It waves when you press a key. Everyone claps. The second one works in a warehouse. It moves boxes for ten hours a day, six days a week. Nobody claps, because it just works. This chapter is about the second kind of robot.

The desk demo and the warehouse robot often run the same math. The difference is the software around the math. The demo runs once, while you watch. The warehouse robot runs thousands of times, while nobody watches. A small bug that you never see in a demo becomes a daily crash in a warehouse.

Production software means code that is ready for real daily work. It starts the same way every time. It checks its own health. It logs what it does. New team members can build it with one command. When something breaks, you can find the cause in minutes, not days.

This chapter gives you that full picture. You will meet the C++ features that professionals use every day. You will meet the math libraries behind robot arms and maps. You will learn how teams build, ship and test code. And you will bring up a real motor joint with ROS 2, step by step.

Why demo code breaks on real robots

A demo script assumes a perfect world. It assumes the camera is always plugged in. It assumes the network never drops. It assumes nobody else touches the files. Real robots live in a messy world, and the mess always arrives.

Think of a food cart versus a restaurant kitchen. The cart serves one dish, cooked by one person, for a few hours. The restaurant serves fifty dishes, cooked by ten people, every single day. The restaurant needs recipes, cleaning lists, delivery plans and health checks. Production software is the restaurant version of your demo cart.

The five enemies of demo code

First, time. A demo runs for two minutes. A product runs for months. Small leaks of memory or disk space grow until the robot freezes at 2 a.m. Second, change. Five people edit the same code. Without rules, they break each other's work daily.

Third, hardware differences. Your laptop is fast. The robot computer is slow and runs a different Linux version. Code that works on your desk fails on the robot. Fourth, timing. A demo tolerates a late answer. A motor controller does not. A late command can shake or damage a real arm.

Fifth, silence. When a demo fails, you are watching. You see the error on screen. When a warehouse robot fails at night, nobody is watching. The robot must record what happened so you can replay the failure the next morning.

The key idea

Production software answers five questions before they become emergencies: Will it run for months? Can a team change it safely? Will it build on any machine? Will it answer on time? Will it explain itself when it fails?

What production adds, in one picture

You already learned the basics of programming your robot in Chapter 14. That chapter taught you to write code that works. This chapter adds the layers that keep code working at scale: safe language habits, tested math libraries, repeatable builds, on-time execution and honest testing.

A useful rule follows from this picture. Write as little as possible. Every line you write is a line you must test and maintain. Every reused library is a line that thousands of other users already tested for you. Professionals are lazy in exactly this smart way.

Modern C++ without fear

Most serious robot software is written in C++. C++ is a language that runs very fast and talks directly to hardware. Its bad name comes from old books. Modern C++ is smaller, safer and friendlier than the C++ of twenty years ago. You only need a few ideas to read and write it well.

If you are new to C++, start with Chapter 14 first. That chapter builds your coding base. Here we add the three habits that separate production C++ from classroom C++.

In simple words

C++ gives you full control of the machine. Modern C++ adds guardrails: owners clean up after themselves, templates stamp out safe copies, and the compiler catches mistakes before the robot moves.

RAII: owners clean up after themselves

RAII is a strange name for a simple habit. It means: the object that takes a resource also frees it. Open a motor port inside an object, and the object's ending closes the port. No separate cleanup call to forget.

Think of borrowing library books with a responsible friend. Your friend returns every book she borrows, automatically, on her way out. You never pay a late fee. In C++, the "friend" is the object's destructor, a small function that runs when the object ends.

The everyday tool for this is the smart pointer. A smart pointer is like a normal pointer, but it remembers to free the memory. Use std::unique_ptr when exactly one owner exists, like one driver owning one motor handle. Use std::shared_ptr when several parts share one object, like several nodes sharing one map. Never write raw new and delete in new code.

Templates: one safe stamp, many uses

A template is a recipe the compiler stamps out for each type you need. You write one safe list class. The compiler makes a list of numbers, a list of poses, a list of motor states. Each stamped copy is checked for errors at build time.

Think of a cookie cutter. You design the star shape once. Then you stamp stars from any dough: plain, chocolate or ginger. The shape stays correct every time. Templates give you the same deal: design the logic once, reuse it for every data type, with full error checking.

You already use templates whenever you write std::vector<double>. That is a stamped list of decimal numbers. Robotics libraries use them everywhere: an Eigen matrix of floats, a vector of joint names, an optional sensor reading that may be missing.

The short list that covers 90 percent

You do not need the whole language. Learn these well and you can read almost any robot codebase. Use const on anything you do not change. Use auto to let the compiler name long types. Pass big objects by const reference instead of copying them. Prefer std::array and std::vector over raw arrays. Handle errors with return values or exceptions, never with silence.

Finally, learn to read compiler errors without panic. The error points at the first line you should check. Read that line slowly. Fix one error and rebuild. Half the remaining errors often vanish, because they were echoes of the first one.

Math toolboxes you should reuse

Robots live in geometry. Arms rotate joints. Cameras project light. Maps fuse noisy sensors. The math behind this is well known, and excellent libraries already implement it. Your job is to pick the right toolbox, not to rewrite the math.

Eigen: fast vectors and matrices

Eigen is the standard C++ library for vectors and matrices. A vector holds a position or a speed. A matrix holds a rotation or a change of frame. Eigen multiplies them fast, using your processor's special math instructions.

Think of Eigen as a pocket calculator that never makes arithmetic slips. You write pose = rotation * point + offset. Eigen checks the sizes match and runs the loop at full speed. Almost every robotics project depends on it, directly or through other libraries.

Two rules keep Eigen friendly. First, keep matrix sizes fixed when you know them, like a 3 by 3 rotation. Fixed sizes run fastest. Second, never access elements one by one in a hot loop if a whole-matrix operation exists. One line of matrix math beats twenty lines of manual loops in both speed and clarity.

Pinocchio: the robot body calculator

Pinocchio computes how a robot body moves. Give it your arm model and the joint angles. It returns where the hand is, how fast each link moves, and which torques gravity demands. It answers the kinematics and dynamics questions from your mechanics chapters in microseconds.

Picture a physiotherapist who knows every bone in your body. You say "my shoulder turned this much", and she tells you exactly where your hand now sits. Pinocchio is that expert for your robot. It reads the standard model file and does the heavy algebra for you.

Tip

Describe your robot once in a URDF model file, then reuse it everywhere: Pinocchio for dynamics, RViz for viewing, Gazebo for simulation. One model, many tools, zero repeated numbers.

Ceres and GTSAM: solvers that agree with noisy data

Sensors lie a little. GPS drifts. Cameras blur. Encoders quantize. Ceres and GTSAM find the answer that best agrees with many imperfect measurements. Ceres is a general nonlinear least-squares solver: it adjusts unknown values until the total error is as small as possible. Think of tuning guitar strings until every string sounds right at once.

GTSAM specializes in robot maps and trajectories. It stores measurements as a factor graph, a web of clues linking poses and landmarks. Then it solves the whole web at once. If you read about smoothing and mapping in Chapter 18, GTSAM is the engine that often powers those ideas in real products.

The plain-words summary: Eigen does the arithmetic, Pinocchio knows the body, Ceres and GTSAM settle arguments between noisy sensors. Learn what each one is for, and reach for it instead of writing your own solver.

From code to robot: builds, containers and CI

Code on your screen is not yet a program. A build turns text files into a running program. A build tool tracks which files changed and rebuilds only what is needed. Without one, you will compile the wrong files and chase ghosts for hours.

CMake: the standard recipe book

CMake is the standard build tool for C++ robotics. You write a short recipe called CMakeLists.txt. The recipe lists your source files, your libraries and your settings. CMake then generates the exact build commands for your machine.

Think of CMake as a recipe card. The card says "cake needs flour, eggs and 30 minutes at 180 degrees". Any kitchen can follow it. Your CMakeLists.txt says "this node needs Eigen, Pinocchio and C++ 17". Any computer can follow it.

CMake 
cmake_minimum_required(VERSION 3.22)
project(arm_driver)

set(CMAKE_CXX_STANDARD 17)

find_package(Eigen3 REQUIRED)
find_package(pinocchio REQUIRED)

add_executable(joint_driver src/joint_driver.cpp)
target_link_libraries(joint_driver Eigen3::Eigen pinocchio::pinocchio)

enable_testing()
add_test(NAME joint_limits COMMAND joint_driver --self-test)

Read it line by line. The first lines name the project and pick the language version. The find_package lines locate your libraries. The add_executable line builds your program. The last lines register a small self-test. Short, readable, repeatable on any machine.

Bazel, Docker and CI: scale the recipe

Bazel is a stricter build tool used by large teams. It tracks every input file exactly, so builds are identical on every machine. It shines when your project has hundreds of parts and several languages. For a small team, CMake is enough. For a company with fifty engineers, Bazel pays off.

Docker solves "works on my laptop". A Docker image is a sealed box holding your OS, libraries and settings. Your code runs inside the same box on your laptop, on the robot and on the test server. A Dockerfile is the recipe that builds the box.

Dockerfile 
FROM ros:jazzy-ros-base
RUN apt-get update && apt-get install -y \
    libeigen3-dev \
    ros-jazzy-ros2-control \
    && rm -rf /var/lib/apt/lists
COPY ./arm_driver /ws/src/arm_driver
WORKDIR /ws
RUN . /opt/ros/jazzy/setup.sh && colcon build

CI, or continuous integration, is a robot that checks every change. Each time you push code, a server builds it, runs the tests and reports green or red. Red means "do not merge yet". This one habit catches most team breakages before they reach any robot.

Note

Cross-compilation builds robot programs on your fast laptop for the robot's slower processor, for example ARM chips. Docker makes this safe: the sealed box holds the robot's toolchain, so the output runs on the robot even though it was built on your desk.

How the pieces fit: a numbered routine

  1. Write code and a CMakeLists.txt recipe on your laptop, and build it locally first.
  2. Push your change. The CI server rebuilds it in a clean Docker box and runs all tests.
  3. When CI is green, the same Docker image is copied to the robot, so the robot runs exactly what was tested.
  4. The robot logs its runs. If something fails, you replay the log on your laptop in the same image.

Notice the promise: laptop, server and robot all run the same sealed box. "But it worked on my machine" stops being an excuse, because every machine is the same machine.

On-time software: real-time Linux and fast buses

Some software may answer late. A web page that loads in two seconds instead of one only annoys you. A motor command that arrives two milliseconds late can shake an arm, overheat a driver or ruin a grasp. Real-time software promises answers before a deadline, every single time.

Why normal Linux is sometimes late

Normal Linux is fair, not punctual. It shares the processor between all programs. Your control loop may wait while the system updates files or draws a window. Usually the wait is tiny. Sometimes it is tens of milliseconds. At a 1 kHz control rate, you only have one millisecond. One surprise wait means one missed command.

Think of a bus that leaves whenever the driver finishes coffee. Most days it leaves nearly on time. Some days it leaves very late. Passengers with flexible plans do not care. A surgeon catching a connecting flight cares a lot. Motor control is the surgeon.

PREEMPT_RT, Xenomai and QNX

PREEMPT_RT is a set of patches that makes Linux punctual. It lets your control task interrupt almost anything else. Worst-case delays drop from milliseconds to tens of microseconds. Most ROS 2 real-time robots run a PREEMPT_RT kernel, because it keeps the familiar Linux tools while adding punctuality.

Xenomai goes further. It runs a tiny, extra-punctual core beside Linux for the most critical tasks. QNX is a separate commercial operating system built for punctuality from the ground up, common in cars and medical devices. Simple rule: start with PREEMPT_RT, and move to Xenomai or QNX only when measurements prove you must.

Warning

Real-time is about the worst case, not the average. A loop that averages 0.2 ms but sometimes takes 5 ms is not real-time. Always measure the maximum delay over thousands of cycles, never the average over ten.

Budget your latency like money

Every control cycle spends time in stages: read sensors, compute commands, send commands. The sum must fit inside the cycle. Write the budget down before you write code, and measure each stage after.

Latency budget Tcycle ≥ Tsense + Tcompute + Tsend + Tmargin

Example: a 1 kHz loop gives Tcycle = 1.0 ms. You measure sensing 0.15 ms, computing 0.25 ms and sending 0.20 ms. The sum is 0.60 ms, leaving a margin of 0.40 ms. That margin absorbs surprises. If the sum ever exceeds 1.0 ms, you must simplify the math, speed the bus or slow the loop, in that order.

EtherCAT and CANopen: the motor highways

Fast loops need fast wires. EtherCAT links many motor drives in one chain with microsecond timing. One message travels through every drive, each one reading and writing on the fly. CANopen is an older, simpler bus, still common on mobile robots and grippers.

Motor drives follow the CiA 402 standard, a shared dictionary of modes and states. The four modes you will use most are:

ModeNameYou send each cycle
8Cyclic synchronous positionTarget angle
9Cyclic synchronous velocityTarget speed
10Cyclic synchronous torqueTarget turning force
6HomingStart signal, drive finds zero itself

ROS 2 in production: nodes, TF2, launch and DDS

You met the core ROS idea in Chapter 18: small programs called nodes that talk through named channels. ROS 2 is the modern version, built for products instead of labs. This section covers the four production pieces: distributions, frames, launch and message tuning.

Humble and Jazzy: pick a long-life version

ROS 2 releases come and go, but LTS releases live for five years. Humble and Jazzy are the two LTS versions you will meet most. Pick one for your whole fleet and freeze it in your Dockerfile. Mixed versions on different robots cause strange, silent message mismatches.

Think of it like truck tires. Any round tire rolls, but a fleet that standardizes on one tire size carries one spare, trains one procedure and never guesses. One ROS 2 version across all robots gives you the same calm.

TF2: every sensor agrees where things are

TF2 tracks the positions of all robot frames over time: base, arm links, camera, gripper. Each node publishes its own piece, and TF2 stitches them into one tree. When your camera sees a box, TF2 tells the arm exactly where that box sits relative to the gripper.

The classic beginner bug is a broken or looping frame tree. Keep one root, usually map or odom, with no cycles. Print the tree with ros2 run tf2_tools view_frames whenever a pose looks wrong. Nine times out of ten, the math is fine and the tree is broken.

Launch files and DDS tuning

A launch file starts your whole system with one command: drivers, controllers, perception and logging, each with its parameters. Without launch files, starting the robot means typing ten commands in the right order and hoping you remember step seven. With them, one file is the whole startup procedure, checked into version control like any code.

Under the messages sits DDS, the delivery service that carries data between nodes. Default settings favor reliability over speed. For fast control topics, switch to best-effort delivery with a small queue, so a late message is dropped instead of piling up. For maps and plans, keep reliable delivery with a deeper queue. Tune per topic, not globally.

Python 
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, QoSReliabilityPolicy, QoSHistoryPolicy
from sensor_msgs.msg import JointState

class JointMonitor(Node):
    def __init__(self):
        super().__init__('joint_monitor')
        # Fast control data: drop late messages, keep only the newest.
        qos = QoSProfile(
            reliability=QoSReliabilityPolicy.BEST_EFFORT,
            history=QoSHistoryPolicy.KEEP_LAST,
            depth=1)
        self.sub = self.create_subscription(
            JointState, 'joint_states', self.on_state, qos)
        self.get_logger().info('Joint monitor started.')

    def on_state(self, msg):
        pos = msg.position[0] if msg.position else 0.0
        self.get_logger().info(f'Joint 0 at {pos:.3f} rad.')

rclpy.init()
node = JointMonitor()
rclpy.spin(node)

This small ROS 2 node watches one joint. It subscribes to the standard joint_states channel with a fast best-effort policy. The newest message always wins. Old messages are dropped, never queued. That is exactly what a live display or safety watcher wants.

ros2_control: one doorway to every motor

ros2_control is the standard doorway between ROS 2 and real motors. Your control algorithm talks to a generic joint handle: "move joint 2 to 0.5 radians". A hardware plugin translates that wish into EtherCAT or CANopen messages for your specific drive. Swap the drive brand, and your algorithm never notices.

Picture a universal travel plug. Your laptop charger stays the same in every country. Only the small adapter changes. ros2_control is the wall socket standard. The hardware plugin is the country adapter. Your controller is the charger that never changes.

  1. Hardware interface reads sensors and writes commands through the bus driver, every cycle, on time.
  2. Controller computes the next command from the joint state, for example a position loop with limits.
  3. Resource manager makes sure only one controller drives each joint at a time, so two commands never fight.
  4. Your nodes send goals and watch states through standard topics, never touching the bus directly.

The concrete driver you will meet below is ethercat_driver_ros2. It connects ros2_control to EtherCAT drives speaking CiA 402. Modes 8, 9 and 10 stream position, velocity or torque targets each cycle. Mode 6 homes the axis first. The worked example walks you through homing, then streaming, on one joint.

Testing: trust, but check four ways

Testing asks one question: does the code do what we claim? Production teams check at four levels, from cheap to precious. Each level catches bugs the cheaper levels cannot see.

The four levels

Unit tests check one tiny function alone. Does the angle wrapper turn 370 degrees into 10? Fast, dozens per second, run on every change. Integration tests check parts working together. Does the planner's path survive the controller's limits? Slower, run before every merge.

HIL tests, or hardware-in-the-loop, plug in real electronics with a fake physical world. The real motor driver runs, but the "motor" is a simulator answering over the bus. This catches timing and wiring bugs without risking hardware. Deterministic replay records real sensor streams once, then replays them bit-for-bit on every build, so a bug fix never depends on luck.

Tip

Record a short "golden log" of joint states and commands from your healthy robot. Replay it in CI every night. If tomorrow's code reacts differently to yesterday's data, you caught a regression before any customer did.

A numbered testing routine

  1. Run unit tests on every save, locally, in under a minute.
  2. Run integration tests on every push, in Docker, before merging.
  3. Run HIL tests nightly on one dedicated test bench with real drivers.
  4. Replay golden logs after every fix, and store any new failure as a new replay.

Each layer is slower and more truthful than the last. Unit tests catch typos in logic. Integration catches broken handshakes. HIL catches timing sins. Replay catches ghosts that only appear on Tuesdays. Together they let you sleep.

Worked example: bring up one EtherCAT joint

Time to put it all together. You have one motor drive on an EtherCAT chain, connected to a Linux computer with PREEMPT_RT. Goal: home the joint, then hold 0.5 radians with ros2_control. Every step shows its reason, so you can repeat it on your hardware.

Step 1. Check the latency budget. Your loop runs at 1 kHz, so Tcycle = 1.0 ms. You measure: sensing 0.15 ms, compute 0.20 ms, bus send 0.25 ms. Sum = 0.60 ms. Margin = 0.40 ms. Positive margin means the loop fits. If any stage measured above budget, you would fix it now, before touching motors.

Step 2. Home the axis in mode 6. Set the CiA 402 mode to 6, homing. The drive moves slowly toward its zero sensor and stops. Read back the actual position. It should sit near zero and stay still. Never skip homing: without a known zero, every later command points at the wrong place.

Step 3. Switch to mode 8 and claim the joint. Set mode 8, cyclic synchronous position. Start the ros2_control resource manager. It claims joint 0 so no other controller can fight you. The hardware interface now streams your target angle every millisecond through ethercat_driver_ros2.

Step 4. Command 0.5 radians and watch. Publish the target on the controller's command topic. Watch joint_states with your monitor node. The position should rise smoothly to 0.5 and stay within 0.01 radians. Check the log for missed cycles: zero missed cycles means your PREEMPT_RT setup holds.

Step 5. Save the proof. Record a ten-second golden log of commands and states. Add it to CI as a replay test. Write the measured stage times into your latency budget document. Tomorrow's changes must beat the same numbers. That is production: every success becomes tomorrow's automatic test.

Common mistakes and how professionals do it

Common mistakes to avoid

Mistake 1: raw new and delete everywhere. Memory leaks for weeks, then the robot dies mid-shift. Fix: use unique_ptr by default and never write manual delete in new code.

Mistake 2: blocking calls in the control loop. One file write or network wait inside the 1 kHz loop blows the whole budget. Fix: do heavy work in a slower thread and pass only small results to the fast loop.

Mistake 3: unpinned library versions. "Latest" Eigen on your laptop differs from the robot's, and builds silently change. Fix: pin every version in your Dockerfile and CI file.

Mistake 4: one global DDS setting. Reliable delivery on a 1 kHz topic piles up old messages until the robot reacts to ancient history. Fix: best-effort with depth 1 for fast topics, reliable for slow plans.

Mistake 5: testing only in simulation. The simulator forgives your timing sins. Fix: run HIL on real drivers weekly, and measure worst-case latency, not average.

How professionals do it

Professionals separate the fast loop from everything else. The real-time thread does three things only: read, compute, write. Logging, networking and file saving happen in slower threads through lock-free queues. This separation is the single biggest difference between lab code and factory code.

They also review every change with a second pair of eyes. A short code review catches unclear names, missing tests and hidden assumptions. They keep a glossary of project terms, like the one in the book glossary, so "joint 0" always means the same motor to everyone. And they read the resources page as a team, so the whole team learns the same tools.

Finally, they practice failure. They unplug a sensor on purpose. They kill a node mid-run. They check that the robot stops safely and the logs explain why. A team that rehearses failure stays calm when failure arrives uninvited.

Going deeper (optional)

Curious readers can study deterministic replay with time travel: record every DDS message with its timestamp, then replay the whole system faster or slower than real time. This turns a rare midnight bug into a movie you can pause, rewind and replay until the cause surrenders.

Try it yourself

  1. Wrap a resource in RAII. Write a small class that opens a file in its constructor and closes it in its destructor. Throw an exception mid-use and confirm the file still closes. Hint: no explicit close call should appear in your test code.
  2. Build the CMake recipe. Copy the CMakeLists block into a tiny project with one Eigen matrix multiply. Build it in a Docker box. Hint: if Eigen is missing, add the dev package to the Dockerfile first.
  3. Measure your own jitter. Write a loop that sleeps 1 ms one thousand times and records the worst overshoot on normal Linux. Hint: print the maximum, not the average, and run a video in the background to make it worse.
  4. Run the monitor node. Start the Python joint monitor against a recorded or simulated joint_states topic. Switch QoS between reliable and best-effort and watch the delay change. Hint: best-effort with depth 1 always shows the newest value.
