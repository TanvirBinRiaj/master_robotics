Programming Your Robot

Hardware gives a robot a body. A program gives it behaviour. In this chapter you will write your first real robot code, upload it, and watch an idea turn into movement.

~26 min read Beginner Chapter 14 of 30

What you will learn

  • Write and upload a simple robot program.
  • Use loops and if-statements to control behaviour.
  • Read and fix a basic error message.

Imagine you have finished building a small robot car. The wheels are on, the motors are wired, the battery is charged. You flip the switch — and nothing happens. The robot just sits there, silent. Nothing is broken. The robot simply has no instructions yet.

A program is what turns a silent pile of parts into a machine that moves. It is the difference between a body and a living creature. In this chapter you stop being only a builder and become a programmer too.

You do not need any prior coding experience. We start from the very first idea: what is a program? Then we add, step by step, every tool you need to make a robot behave. By the end you will have written a complete obstacle-avoiding robot, line by line, in your own words.

What a program really is

A program is a list of instructions that a computer runs in order, from top to bottom. That is the whole idea. Each instruction tells the robot to do one small thing. The computer reads the first line, does it, then reads the next line, and so on.

Here is the part that surprises beginners: the robot has no common sense. It does not know that hitting a wall is bad. It does not know that a motor should not spin forever. It does exactly what you wrote — nothing more, nothing less.

If you write "go forward", it goes forward, even into a wall. If you forget to tell it to stop, it never stops. The robot is a very obedient, very literal servant. Your job is to give it clear orders.

The key idea

A program is a precise list of steps. The robot follows every step exactly. If the behaviour is wrong, the instructions were wrong — not the robot.

Instructions are run in order

Order matters. Read these two lists and notice how different they feel:

  1. Spin the left wheel forward.
  2. Spin the right wheel backward.

That pair makes the robot turn. Now swap them:

  1. Spin the right wheel backward.
  2. Spin the left wheel forward.

The robot still turns, because both wheels move at nearly the same time. But some orders are not forgiving. "Drive forward" then "read the distance" gives you different information than "read the distance" then "drive forward". One robot looks before it moves. The other moves first and looks later. On a real robot, that difference can mean a bump or a safe stop.

In simple words

A program is a recipe. The robot is a cook who follows it exactly, in order, and never improvises. Write a clear recipe and you get a clear result.

The two parts of every Arduino program

Most beginner robots use a small board, like an Arduino. An Arduino program is called a sketch. Every sketch, no matter how big, has two special sections: setup() and loop().

setup() — the part that runs once

setup() runs one time, right after the board powers on or resets. It is the place for preparation. You tell the board which pins are inputs and which are outputs. You start the serial connection. You set starting values. Then setup finishes and never runs again.

Think of it as the pre-flight checklist of an aeroplane. You do it once, carefully, before anything moves.

loop() — the part that runs forever

loop() runs over and over, forever, until you remove the power. When it reaches the last line, it jumps straight back to the first line and starts again. This is the robot loop you met in Chapter 1: sense, decide, act, repeat.

This is why the design fits robots so perfectly. You do not write "do this, then finish". You write "do this, then do it again". The board takes care of the repeating for you.

Note

If you forget to write loop(), your program might still build, but the robot will do nothing after setup. If you forget setup(), it may not build at all. Both parts must exist, even if one is empty.

Variables: named boxes for your robot's numbers

A robot constantly handles values: the distance to a wall, the speed of a motor, whether a button is pressed. Before you can use a value, you need somewhere to keep it. That somewhere is a variable.

A variable is a named box that holds one value. You give the box a name, put a value inside, and later you can read it or change it. The name is for you, the human. The robot only cares about the value inside.

Good names make code easy to read. distance is a good name. d is a bad name — you will forget what it meant next week.

The four simple types

In Arduino code you say what kind of value a box holds. This helps the board store it correctly. Four types cover almost everything a beginner needs.

Creating and changing a variable

To create a variable you write the type, then the name, then a value. This is called declaring the variable. After that you can change it whenever you like.

Arduino C++ 
int distance = 0;        // a whole number, starts at 0
float speed = 0.5;       // half speed
bool wallAhead = false;  // no wall seen yet
String label = "SONAR";  // text in quotes

distance = 42;           // now the box holds 42
wallAhead = distance < 30;  // true, because 42 is not less than 30? it is false!

Read the last line carefully. distance < 30 asks a question. Because distance is 42, the answer is false. So wallAhead becomes false. The single equals sign means "put this value in the box". We will meet the double equals sign soon, and the difference matters a lot.

Tip

Give variables honest names. distanceToWall tells you everything. x tells you nothing. Your future self will thank you when the code grows long.

Reading the world and moving it: inputs and outputs

A robot spends its life doing two jobs: reading inputs and writing outputs. An input is information coming in from a sensor. An output is an action going out to a motor, light or buzzer. The functions below are the basic tools for both.

Digital and analog — two kinds of signal

A digital signal has only two states: on or off, high or low, true or false. A button is digital — it is pressed or not pressed. An analog signal can have many values in a range, like a light level that is dim, medium or bright.

Reading inputs

digitalRead(pin) reads a digital input. It answers with HIGH or LOW. Use it for buttons and switches — anything that is simply on or off.

analogRead(pin) reads an analog input. It gives a number, usually from 0 to 1023. Use it for light sensors, knobs and other parts that give a range.

Writing outputs

digitalWrite(pin, value) sets a digital output to HIGH or LOW. Use it to switch an LED on or off, or to make a motor turn at full speed in one direction.

analogWrite(pin, value) sets an analog output using a trick called PWM, short for Pulse Width Modulation. It does not really give you a smooth range of voltage. Instead, it switches the pin on and off very fast. By changing how long it stays on, it fakes a middle value. Think of a light switch flicked so quickly that the room looks half bright.

In simple words

Digital is a light switch: on or off. Analog is a dimmer knob: many levels. analogWrite gives a motor a speed between stopped and full using fast on-off switching.

With analogWrite, the value runs from 0 to 255. Zero means off. 255 means full speed. 128 means about half. That is how you make a robot move slowly and gently instead of always slamming into full speed.

Pins must be prepared first

Before you read or write a pin, you must tell the board whether it is an input or an output. You do this once in setup() using pinMode(pin, mode).

Arduino C++ 
// --- inside setup(), runs once ---
pinMode(2, INPUT);    // pin 2 reads a button
pinMode(3, INPUT);    // pin 3 reads the distance sensor
pinMode(9, OUTPUT);   // pin 9 drives an LED
pinMode(10, OUTPUT);  // pin 10 drives the left motor
pinMode(11, OUTPUT);  // pin 11 drives the right motor

If you forget pinMode, the pin behaves in a default way that may not match your wiring. The robot may read nonsense or fail to drive a motor. Setting the mode is a small habit that saves big confusion.

Making decisions: if and else

A robot that only runs fixed instructions is not very clever. The power comes when it can choose. The tool for choosing is the if-statement. It asks a question, and does something only when the answer is true.

Here is the shape in plain words: "if this is true, do that." In code it looks like this:

Arduino C++ 
int distance = analogRead(3);

if (distance < 30) {
  turnLeft();          // wall is close, so turn
}

if (distance < 30) {
  turnLeft();
} else {
  goForward();         // otherwise keep going
}

The first block does nothing when the wall is far. The second block always does one of the two actions, because else covers every other case. Most robot logic uses the second shape, because a robot always needs to be doing something.

Comparison operators

The question inside an if-statement uses a comparison operator. These are the symbols that compare two values. This table is worth remembering.

Danger

Do not mix up = and ==. A single = stores a value. A double == compares two values. Writing if (x = 5) by mistake stores 5 in x instead of comparing. The robot then behaves strangely, and the error is hard to see. This is one of the most common beginner bugs.

Combining conditions with and / or

Sometimes one question is not enough. You may want two things to be true at once, or either of two things to be true. You join conditions with && for AND, and || for OR.

&& (AND) means both sides must be true. || (OR) means at least one side must be true. A real robot example:

Arduino C++ 
// only turn if the wall is close AND the path on the left is open
if (frontDistance < 30 && leftDistance > 40) {
  turnLeft();
}

// stop if the bumper is pressed OR the battery is almost empty
if (bumperPressed || batteryLow) {
  stopMotors();
}

Read the first one aloud: "If the wall in front is close, and the left side has room, then turn left." That single line is a small piece of machine judgement. This is how robots make choices.

Loops: doing things again and again

A robot repeats actions constantly. You could copy the same line a hundred times, but that would be silly and hard to change. Instead you use a loop. A loop repeats a block of code. There are three kinds you will use most.

for loop — repeat a known number of times

Use a for loop when you know in advance how many times to repeat. For example, blink a light five times, or sweep a servo through ten steps.

Arduino C++ 
// blink the LED 5 times
for (int i = 0; i < 5; i++) {
  digitalWrite(9, HIGH);  // LED on
  delay(200);             // wait 200 ms
  digitalWrite(9, LOW);   // LED off
  delay(200);
}

The line for (int i = 0; i < 5; i++) creates a counter i that starts at 0. It repeats while i is less than 5, and adds 1 to i after each pass. So the block runs 5 times, with i equal to 0, 1, 2, 3, 4.

while loop — repeat while a condition holds

Use a while loop when you do not know the number of repeats ahead of time. You repeat as long as a condition stays true. This is useful for "keep doing this until something changes".

Arduino C++ 
// spin up while the button is held down
while (digitalRead(2) == HIGH) {
  analogWrite(10, 200);   // keep the motor running
}
analogWrite(10, 0);       // button released, stop
Watch out

If the condition in a while loop never becomes false, the loop never ends. The robot freezes and ignores everything else. Always make sure something inside the loop can change the condition. A frozen robot often means a runaway while loop.

The forever loop()

The loop() function is itself a forever loop. You write its contents once, and the board repeats them endlessly. You never need to write "repeat forever" yourself — the board does it for you. That is why the main behaviour of a robot lives inside loop().

The difference is simple. A for loop runs a set number of times. A while loop runs until a condition changes. The loop() function runs until the power is cut. Master these three and you can shape any robot behaviour.

Loop rate loops per second = 1000 ÷ (time for one loop in milliseconds)

This small formula tells you how fast your robot thinks. If one full loop takes 10 milliseconds, the robot loops 100 times per second. If one loop takes 500 milliseconds, it loops only twice per second — far too slow to dodge a moving obstacle. We will use this idea again when we talk about delay().

Functions: naming a block of code

As your code grows, you will repeat the same group of lines many times. Perhaps you have five lines that make the robot turn left. Writing those five lines everywhere is messy and easy to get wrong. The answer is a function.

A function is a named block of code. You give the block a name, and afterwards you can run the whole block just by writing its name. That is called calling the function.

Arduino C++ 
// the definition: write the block once and give it a name
void turnLeft() {
  analogWrite(10, 0);     // left motor off
  analogWrite(11, 180);   // right motor forward
  delay(300);             // let it turn for a moment
}

// later, in loop(), run the whole block with one short line
turnLeft();

The word void means "this function gives back no value". It just does a job. The empty parentheses mean it needs no information to start. When you write turnLeft(); in your main code, all five lines run.

Why functions make code readable

Compare two versions of the same robot. One repeats the turning lines six times. The other defines turnLeft() once and calls it six times. The second version is shorter, easier to read, and much easier to fix. If you decide the turn should last longer, you change one number in one place instead of hunting through the whole file.

Functions also give your code a vocabulary. When you read turnLeft(); goForward(); stopMotors();, you understand the robot's behaviour at a glance. That is the goal of good code.

Comments: notes for your future self

A comment is a note inside the code that the robot ignores completely. Comments are only for humans. In Arduino code there are two ways to write one.

Arduino C++ 
// This whole line is a comment. The robot skips it.

int distance = 0;   // A comment can also sit at the end of a line.

/* This is a longer comment.
   It can cover several lines.
   Use it to explain a whole section. */

Two slashes // comment out the rest of that line. Slash-star /* ... */ comments out everything between the markers, across many lines.

Why bother? Because in three weeks you will not remember why you wrote a strange number. A comment like // 30 cm is the safe stopping gap explains it instantly. Comments are a gift to your future self, who will have forgotten everything.

Tip

Comment the why, not the what. // turn left above turnLeft(); wastes a line. // turn left because the right side is blocked tells you something the code cannot.

The serial monitor: your window into the robot

How do you know what your robot is thinking? You cannot see the value inside a variable just by looking at the board. The answer is the serial monitor. It is a window in your computer that shows messages sent from the robot.

Think of it as a one-way chat from the robot to you. The robot sends a line of text, and it appears on your screen. This is the single most useful debugging tool a beginner has.

You start it once in setup(), then send messages with Serial.print() or Serial.println().

Arduino C++ 
void setup() {
  Serial.begin(9600);   // start the chat at 9600 bits per second
}

void loop() {
  int distance = analogRead(3);

  Serial.print("Distance: ");   // print text, no line break
  Serial.println(distance);     // print the value, then start a new line

  delay(500);
}

Serial.print() prints and stays on the same line. Serial.println() prints and then jumps to the next line. Used together, the example above prints something like Distance: 42 every half second. You can watch the number change as you move your hand in front of the sensor.

In simple words

The serial monitor is the robot talking to you. When you are confused about what the robot sees, make it print the values. The problem usually becomes obvious at once.

Structuring robot code: read, decide, act

Before the worked example, fix one habit in your mind. Nearly every good robot loop follows the same three-part shape you learned in Chapter 1.

  1. Read all the inputs you need first. Read the distance. Read the bumper. Read the battery.
  2. Decide what to do, using if-statements based on those readings.
  3. Act on the decision — set motor speeds, lights or sounds.

Then let loop() start again. Always read before you decide, and decide before you act. If you act first and read later, your robot is always reacting to yesterday's information, and it will feel clumsy and slow.

Note

Professionals call this pattern the sense-decide-act loop. It is the same idea in Chapter 1, now written in code. Keep it in this order and your programs stay clear and easy to debug.

A full worked example: an obstacle-avoiding robot

Now we build a complete program together. Our robot has two motors and one forward-facing distance sensor. The goal: drive forward, but turn away before hitting anything. We build it in five small steps, so you can see how a program grows.

Step 1 — say what the robot must do

In plain words: "Drive forward. If something is closer than 30 cm, turn right for a moment, then keep going. Never stop reading the distance." Every program should start with a sentence like this. It is your contract with yourself.

Step 2 — plan the pins

We choose pins and write them down so we never get confused. The distance sensor is on analog pin 3. The left motor is on pin 10, the right motor on pin 11. This plan goes into setup().

Step 3 — write the first simple version

Start small. This version reads the distance and decides. It uses a named constant for the threshold, so the number has a meaning.

Arduino C++ 
const int SENSOR_PIN = 3;      // distance sensor input
const int LEFT_MOTOR = 10;     // left motor output
const int RIGHT_MOTOR = 11;    // right motor output
const int SAFE_GAP = 30;       // cm: turn if closer than this

void setup() {
  pinMode(SENSOR_PIN, INPUT);
  pinMode(LEFT_MOTOR, OUTPUT);
  pinMode(RIGHT_MOTOR, OUTPUT);
  Serial.begin(9600);          // open the chat to your computer
}

void loop() {
  int distance = analogRead(SENSOR_PIN);  // 1. READ

  if (distance < SAFE_GAP) {              // 2. DECIDE
    analogWrite(LEFT_MOTOR, 180);         // 3. ACT: turn right
    analogWrite(RIGHT_MOTOR, 0);
  } else {
    analogWrite(LEFT_MOTOR, 180);         // 3. ACT: go forward
    analogWrite(RIGHT_MOTOR, 180);
  }
}

This already works, but it has a flaw. The moment the wall is far again, the robot snaps straight back to full forward. It will jitter at the 30 cm boundary. Real robots need a little smoothing.

Step 4 — improve with functions and a turn timer

We tidy the code using functions, and we make the turn last a short fixed time using delay(). Functions keep the loop readable; the delay makes the turn deliberate.

Arduino C++ 
const int SENSOR_PIN = 3;
const int LEFT_MOTOR = 10;
const int RIGHT_MOTOR = 11;
const int SAFE_GAP = 30;
const int CRUISE = 180;        // normal forward speed

void goForward() {
  analogWrite(LEFT_MOTOR, CRUISE);
  analogWrite(RIGHT_MOTOR, CRUISE);
}

void turnRight() {
  analogWrite(LEFT_MOTOR, CRUISE);   // left wheel forward
  analogWrite(RIGHT_MOTOR, 0);       // right wheel stopped
}

void setup() {
  pinMode(SENSOR_PIN, INPUT);
  pinMode(LEFT_MOTOR, OUTPUT);
  pinMode(RIGHT_MOTOR, OUTPUT);
  Serial.begin(9600);
}

void loop() {
  int distance = analogRead(SENSOR_PIN);   // READ
  Serial.println(distance);                // report what we saw

  if (distance < SAFE_GAP) {               // DECIDE
    turnRight();                           // ACT
    delay(300);                            // keep turning briefly
  } else {
    goForward();                           // ACT
  }
}

Step 5 — walk through the code line by line

  1. The constants. The first five lines give names to fixed values: the pins, the safe gap and the cruise speed. Names beat mystery numbers.
  2. The functions. goForward() and turnRight() each hold one small behaviour. The loop reads like a story because of them.
  3. setup(). It sets the sensor as an input, the motors as outputs, and opens the serial monitor. Each line runs once.
  4. Read the distance. analogRead(SENSOR_PIN) gives a number. We store it in distance.
  5. Report it. Serial.println(distance) sends the number to your screen so you can watch it live.
  6. Decide. The if-statement compares distance with SAFE_GAP.
  7. Act. Close wall: turn for 300 ms. Clear path: drive forward. Then loop() starts again.

You have just written a real robot behaviour. It senses, decides and acts, forever. Every robot vacuum, delivery bot and warehouse machine does a more advanced version of exactly this.

Time and speed: why delays can freeze your robot

Look back at Step 4. We used delay(300) to make the turn last. delay() pauses the whole program for that many milliseconds. It is simple and useful. But it has a serious downside: while the robot is delayed, it does nothing else.

During those 300 milliseconds the robot cannot read the distance. It cannot check the battery. It cannot hear a stop button. It is blind, deaf and frozen. Engineers call this blocking code, because it blocks everything else. A delay(1000) freezes the robot for a whole second — a very long time on a moving robot.

Watch out

Long delays are one of the most common beginner mistakes. They feel harmless on a bench, but on a real robot they mean missed readings and late reactions. Use short delays, and learn the non-blocking trick below for anything longer.

The idea of non-blocking code with millis()

millis() gives the number of milliseconds since the board powered on. It keeps counting up in the background, all the time, whether you read it or not. That lets you ask a clever question: "Has enough time passed yet?" — without ever pausing.

Instead of "stop for 300 ms", you say "remember the time the turn started, and keep checking whether 300 ms have gone by". While you check, you can keep reading sensors. Nothing is frozen.

Arduino C++ 
// BEFORE (blocking): the robot is blind for 300 ms
turnRight();
delay(300);

// AFTER (non-blocking): keep watching the world while turning
unsigned long turnStarted = millis();   // note the start time

// later, still inside loop():
if (millis() - turnStarted < 300) {
  turnRight();          // still within the turn window
} else {
  goForward();          // turn finished, carry on
}

Both versions turn for 300 milliseconds. The difference is that the non-blocking version never stops reading the world. On a fast robot, that is the difference between reacting in time and crashing.

Loop rate rate (Hz) = 1000 ÷ loop_time_ms

Use this to check your robot's thinking speed. A loop with no delay might take 5 ms, giving 200 loops per second — fast and responsive. Add delay(500) and the same loop does 2 per second — sluggish and unsafe. Keep your loop time small.

Reading and fixing errors

Errors are normal. Every programmer, beginner and expert, sees them all the time. The skill is not avoiding errors; it is reading them calmly and fixing them quickly. Most errors you meet as a beginner come from the compiler.

What a compiler error means

Before your code can run, a tool called the compiler reads it and translates it into the robot's language. If the compiler finds something it cannot understand, it stops and prints an error message. That message usually has two useful parts: a line number, and a description.

The line number tells you where to look. Sometimes the real mistake is on the line before, because the compiler only noticed it later. Start at the first error shown, fix it, then build again. Later errors are often caused by the first one.

A broken snippet and its fix

Here is a program with two mistakes. Read it and try to spot them before looking at the fix. Remember: the robot is a literal reader, and the compiler is even stricter.

Arduino C++ 
void setup() {
  pinMode(10, OUTPUT)
}

void loop() {
  digitialWrite(10, HIGH);
}

The errors: the pinMode line is missing its semicolon, and digitialWrite is misspelled. Here is the fixed version:

Arduino C++ 
void setup() {
  pinMode(10, OUTPUT);       // semicolon added
}

void loop() {
  digitalWrite(10, HIGH);    // spelling fixed
}

A step-by-step debugging routine

When something is wrong, follow these steps in order. Do not skip around or change many things at once.

  1. Read the first error. Note the line number and the exact words. Do not panic at a long list; fix the top one first.
  2. Look at that line and the one above. The cause is often just before where the compiler complains.
  3. Check the three usual suspects. Missing semicolon, wrong spelling or case, missing brace.
  4. Fix one thing. Change a single item, then build again. One change at a time tells you what worked.
  5. If it still fails, comment out the last few lines you added, confirm it builds, then add them back in small pieces to find the culprit.
  6. Once it builds, upload it and open the serial monitor. Use prints to see what the robot actually reads.
Tip

The error message is your friend, not your enemy. Read it slowly. It almost always tells you exactly what kind of mistake it found and roughly where. The skill is patience, not cleverness.

Common mistakes beginners make

Every programmer has made all of these. Knowing them in advance saves you a lot of head-scratching.

  • Using long blocking delays. delay(2000) freezes the robot for two seconds. It cannot sense or react. Use short delays, or get into the habit of millis().
  • Magic numbers with no names. Writing if (distance < 30) everywhere leaves everyone wondering what 30 means. Name it: const int SAFE_GAP = 30;.
  • No comments. Code you cannot understand two weeks later is code you cannot fix. Add a short comment wherever the reason is not obvious.
  • Ignoring the serial monitor. Beginners guess at what the robot sees. Printing the values shows you the truth in seconds.
  • Copy-pasting without understanding. Code you copied but do not understand will break the moment you need to change it. Type examples out and read every line.
  • Acting before reading. Writing motor commands at the top of loop() and reading sensors at the bottom means your robot always reacts to stale information.
  • Mixing up = and ==. Store versus compare. This bug produces no error message and strange behaviour, so it is easy to miss.

How professionals do it

The professional's code looks cleaner than the beginner's, but it is built from the same pieces you just learned. What changes is discipline and a few strong habits.

State machines

As behaviour grows, a long chain of if-statements becomes hard to follow. Professionals use a state machine. The robot is always in exactly one state — for example DRIVING, TURNING or STOPPED. Each state has its own rules for what to do and when to switch. This keeps a complex robot understandable, and you will meet it properly in Chapter 15.

Code style that others can read

Professionals follow a consistent style: clear names, small functions, one job per function, and comments where the reason matters. Code is read far more often than it is written, so making it easy to read is a real skill, not a luxury.

Version control

Professionals keep every version of their code in a system called version control, usually Git. Each change is saved with a short message. If a new idea breaks the robot, they can return to a working version in seconds. It also lets a team work on the same code safely.

Testing on real hardware

A program can be perfect on the computer and still misbehave on the real robot, because real sensors are noisy and real motors are not identical. Professionals test on hardware early, then again after every change. This idea is sometimes called hardware-in-the-loop testing.

Watchdogs and safe behaviour

A watchdog is a safety timer. If the program ever freezes or crashes, the watchdog notices that it stopped checking in, and it restarts the board. Professionals also design safe behaviour for failure: if a sensor dies, the robot stops rather than driving blind. A safe robot is one that fails in a safe way.

The key idea

Professional code is not smarter code. It is clearer code, tested more often, and written so that the next person — including future you — can understand and trust it.

Try it yourself

These exercises go from easy to harder. If you have a board, try them for real. If not, write the code and trace it line by line on paper — that is excellent practice too.

  1. Blink on and off. Write a program that turns an LED on for half a second, then off for half a second, forever. Hint: use digitalWrite and delay(500) inside loop().
  2. Add a condition. Use a button and an LED. Turn the LED on only while the button is pressed. Hint: if (digitalRead(2) == HIGH) { ... }.
  3. Name your numbers. Take exercise 2 and replace every raw pin number and delay with a named const int. Hint: const int BUTTON_PIN = 2;.
  4. Turn with a function. Write a turnLeft() function that spins one motor and stops the other, then call it from loop() when a distance reading is small. Hint: analogWrite with 0 and 180.
  5. Print then fix. Deliberately remove a semicolon and a brace from your working program, build it, and read the errors. Write down what each message told you, then fix both. Hint: the compiler usually names the line where it first got confused.

Going deeper: from blocking to event-driven

This next idea is optional, but it is the doorway to professional control. Instead of writing "do this, then wait", advanced robot code is event-driven. The loop runs extremely fast, and on every pass it simply checks: is it time to do the next thing? Is a new reading ready? Has nothing changed for a while? Nothing ever blocks, so the robot stays responsive at all times. The millis() trick you just learned is the first step on this path, and state machines are the next.

Key takeaways

  • A program is a list of instructions the robot runs in order, with no common sense of its own.
  • Every Arduino sketch has setup(), which runs once, and loop(), which runs forever.
  • A variable is a named box that holds a value; the type says what kind of value.
  • Inputs are read with digitalRead and analogRead; outputs are written with digitalWrite and analogWrite.
  • Use if / else to choose, and loops to repeat. Name reusable blocks as functions.
  • Long delay() calls freeze the robot; millis() lets it keep sensing while it waits.
  • Read the first compiler error, fix one thing, and rebuild. Print values to the serial monitor to see the truth.
Check your understanding
Q1.What is a program, in one plain sentence?
Answer. A program is a list of instructions that a computer runs in order, from top to bottom.
Q2.What is the difference between setup() and loop()?
Answer. setup() runs once, right after power-on, for preparation. loop() runs over and over forever, and holds the robot's sense-decide-act behaviour.
Q3.Which variable type would you use to store whether a bumper is pressed?
Answer. A bool, because the answer is only true or false.
Q4.Why is analogWrite described as a trick?
Answer. Because the pin cannot truly output a middle voltage. It switches on and off very fast (PWM), and the motor feels the average. That fakes a speed between off and full.
Q5.Why must you call pinMode before using a pin?
Answer. To tell the board whether the pin is an input or an output. Without it, the pin uses a default that may not match your wiring, causing wrong readings or no output.
Q6.What is the difference between a for loop and a while loop?
Answer. A for loop repeats a known number of times. A while loop repeats while a condition stays true, which is useful when you do not know the count in advance.
Q7.Why is delay(1000) dangerous on a moving robot?
Answer. It blocks the whole program. For one second the robot cannot read sensors or react to anything. On a moving robot that can mean a missed obstacle or a crash. millis() waits without freezing.
Q8.A compiler says expected ';' before '}' on line 7. What do you do first?
Answer. Go to line 7, and also check the line just above it. A statement is probably missing its semicolon. Add it, then build again before changing anything else.
